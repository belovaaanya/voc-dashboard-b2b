# Валидация референсного макета

Референсный wireframe (`3204:2682`) передаёт **композицию и намерение**, но не
годится как источник пиксельных значений и цифр: часть геометрии не сходится,
часть данных противоречит сама себе.

Ниже — расхождения, найденные при сверке node-метаданных Figma с отрендеренным
макетом, и принятое решение по каждому. **Перед реализацией блока сверьтесь с
этим списком:** макет в этих местах воспроизводить не нужно.

Обозначения: `ID` — ссылка для обсуждений и PR; `Node` — узел Figma, на котором
расхождение видно.

---

## 1. Геометрия и сетка

### V-01 — правые края строк не совпадают и не добирают контентную колонку

Строка метрик: `356 + 16 + 664 + 16 + 338 = 1390`.
Основная область: `1037 + 12 + 346 = 1395`.
Контентная колонка — `1400`.

Правый рейл меняет ширину между строками: `338` в метриках против `346` в
основной области, из-за чего правые края блоков не выстраиваются в линию.

**Решение.** Задаём сетку на своей стороне: единая ширина правого рейла,
колонки в сумме дают `1400`. Значения макета не переносим.

### V-02 — несогласованные зазоры

В одном макете используются `8` (между малыми карточками), `12` (между
строками и колонками основной области) и `16` (между большой карточкой и
группой малых).

**Решение.** Одна шкала отступов, кратная `4`; зазор между равноправными
элементами одинаковый.

### V-03 — разная ширина карточек в одной колонке

Карточка графика — `1034`, карточка heatmap — `1037`, обе внутри контейнера
`1037`: левая колонка «дышит» на `3 px`. Высота левой колонки `647` против
`649` у правой.

**Node.** `3204:2865` (график), `3204:3029` (heatmap).

**Решение.** Карточки в колонке — одной ширины, растягиваются по контейнеру.

### V-04 — разделители фильтров содержат чужие подписи

Разделители в панели фильтров — фреймы шириной `1`, внутри которых лежит
полноразмерный текст с отрицательным `x`, то есть заведомо за границами
контейнера:

| Node | Ширина фрейма | Текст внутри | X текста |
| --- | --- | --- | --- |
| `3204:2703` | `1` | `01.05.26 - 31.05.26` | `−42.5` |
| `3204:2707` | `1` | `Розничный сектор` | `−41` |
| `3204:2711` | `1` | `Менеджеры` | `−27.5` |
| `3204:2715` | `1` | `КП №1` | `−15.5` |
| `3204:2719` | `1` | `Сценарий A` | `−27` |

Визуально они рендерятся как точки-разделители `·`, но несут подписи из другого
состояния макета.

**Решение.** Разделитель — декоративный `1 px` divider без содержимого.
Значения фильтров приходят из `dim_filters`
([data-model 3.1](data-model.md#31-dim_filters--справочник-фильтров)),
а не из макета.

### V-05 — сетка и серии графика выходят за область построения

Внутри `graf` (`952 × 199`):

- группа линий `3204:2910` размещена на `y = 201` при высоте `204` — целиком
  ниже области построения;
- группа линий `3204:2933` — `y = −3`, высота `204` при высоте родителя `199`;
- векторы серий `3204:2949`, `3204:2950`, `3204:2951` — ширина `959` в
  контейнере `952`.

**Решение.** Область построения обрезает содержимое; линии сетки выводятся из
шкалы Y, а не рисуются отдельными узлами.

### V-06 — подписи значений графика лежат вне графика

Компоненты `NUM` (`3204:3061` … `3204:3103`) — дети корневого артборда, а не
карточки графика, и позиционированы абсолютно (`x = 504…963`, `y = 441…647`).
Они визуально лежат поверх графика, но структурно к нему не относятся, поэтому
при любом изменении данных или размера разъедутся.

**Решение.** Подписи точек — часть рендерера серии.

### V-07 — текстовый узел ниже области построения

`3204:2953` находится на `y = 220` внутри фрейма высотой `199`.

**Решение.** Артефакт макета, не воспроизводим.

### V-08 — текст шире родителя в малых карточках

`Frame 104` шириной `41.33` содержит заголовок шириной `54…69`;
`Frame 105` шириной `91` содержит значение шириной `99…102`.

**Node.** `3204:2740`, `3204:2762`, `3204:2784`.

**Решение.** Auto-layout по фактической ширине содержимого.

### V-09 — trend-иконка выровнена по-разному

В карточках 1 и 3 иконка на `y = 0.5`, в карточке 2 — на `y = 16.5`.

**Node.** `3204:2772` против `3204:2750`, `3204:2794`.

**Решение.** Единое выравнивание для всех карточек.

### V-10 — в файле остались скрытые слои

| Node | Что это |
| --- | --- |
| `3204:2683` | placeholder-картинка `1241 × 1882` |
| `3204:2804` | второй, неиспользуемый набор карточек метрик |
| `3204:3047` | `Heatmap Digit Values` |
| `3204:3039` | прежний переключатель `Продукты` / `Триггеры` |
| `3204:2727`, `3204:2742`, … | скрытые инстансы `MetricCell/Indicator` |

**Решение.** Не контент, в реализацию не попадают. Важно при чтении макета не
принять их за требования.

## 2. Данные и смысл

Эти расхождения важнее геометрии: если перенести их в тестовые данные, первый
же расчёт на клиенте будет выглядеть как баг реализации.

### V-11 — период в шапке не совпадает с периодом графика

Шапка: `12.03.26 - 23.04.26` (март–апрель). Ось X графика: `12.05.26 … 22.05.26`
(май). В карточке heatmap та же шапка `12.03.26 - 23.04.26`, а колонки
подписаны `12.05`.

**Решение.** Период — единый сквозной контекст
([requirements 2.1](requirements.md#21-период--сквозной-контекст-а-не-фильтр));
подписи блоков выводятся из выбранного периода, а не задаются вручную.

### V-12 — подписи оси X дублируются и идут вспять

`12.05, 13.05, 14.05, 15.05, 16.05, 16.05, 16.05, 17.05, 18.05, 19.05, 20.05,
21.05, 22.05, 18.05, 16.05` — три раза `16.05`, последние две метки нарушают
порядок.

**Решение.** Ось X строится из данных.

### V-13 — бейдж противоречит плану

Значение `4.90` при `План: 4,69 - 4,78` выше коридора, но бейдж читается
`В плане`.

**Решение.** Состояние бейджа вычисляется сравнением значения с
`voc_plan.plan_min` / `plan_max`. В тестовых данных коридор задаётся так, чтобы
бейдж был правдив.

### V-14 — сегменты не сходятся с каналом

`4.96 / 4.66 / 4.96` при `1 459 / 1 459 / 12` оценок дают взвешенное среднее
≈ `4.81` на `2 930` оценках, тогда как карточка канала показывает `4.90` на
`10 459` оценках.

**Решение.** VOC канала — взвешенное по `ratings_count` среднее по сегментам
([data-model 3.2](data-model.md#32-voc_daily--voc-и-объём-выборки-по-дням)).
Тестовые данные сходятся по определению.

### V-15 — знак дельты противоречит направлению тренда

`VOC СБ` показывает падение (стрелка вниз, отрицательный цвет) при дельте
`+0,04`. Кроме того, два сегмента имеют одинаковый объём `1 459` оценок.

**Решение.** Направление и цвет тренда выводятся из знака дельты, а не задаются
отдельно.

### V-16 — панель выводов противоречит рейтингу антидрайверов

Панель: рост за счёт `АЗОН` и `Лояльности`. Рейтинг в спецификации:
`Лояльность` — антидрайвер с вкладом `−0,05`.

**Решение.** За основу берётся текст спецификации (рейтинг), панель выводов
формируется из тех же данных, что и рейтинг, — расхождение станет
невозможным. **Требует подтверждения заказчика**, если `Лояльность`
действительно драйвер роста.

### V-17 — список событий заполнен одинаковыми заглушками

Все пять строк: дата `18.05.26`, дельта `+0,04`, значение `4,78 VOC`, причина
`Выписка, Платежи`. При этом строка с тегом `Резкое падение VOC` несёт
положительную дельту `+0,04`.

**Решение.** Знак `delta_voc` обязан соответствовать `kind`; в тестовых данных
это проверяется скриптом
([data-model 5](data-model.md#5-тестовые-данные)).

### V-18 — heatmap: одинаковые подписи колонок, заливка не связана со значением

Все 10 колонок подписаны `12.05`. Значения повторяют `4,48` / `4,83`, при этом
одно и то же число залито зелёным, малиновым и нейтральным.

**Решение.** Подписи колонок — из данных; заливка — монотонная функция
значения, одна шкала на всю карту.

### V-19 — горизонтальный скроллбар при умещающейся сетке

Под heatmap выведен скроллбар `1005 × 7`, хотя сетка укладывается в контейнер.

**Решение.** Скроллбар появляется, только когда колонок больше, чем влезает.

## 3. Замечание к тексту спецификации

### V-20 — раздел 10 продублирован

В текстовой спецификации заголовок «10. Интерактивность и фильтрация» и первая
фраза раздела идут дважды. Содержательной разницы между копиями нет — в
[requirements](requirements.md) раздел сведён в один.

## 4. Что с этим делать

1. Геометрию (`V-01`…`V-10`) не переносим: сетка, отступы и структура
   компонентов задаются в коде.
2. Числа (`V-11`…`V-19`) не переносим: тестовые данные обязаны быть
   непротиворечивыми, а показатели — вычисляемыми из фактов.
3. Композицию, состав блоков и визуальный язык (тёмная тема, акцентная пара
   зелёный/малиновый, pill-ячейки, крупное значение метрики) — берём из макета:
   здесь он и есть источник.
4. Новые расхождения дописываем сюда с новым `ID` — список живой.
5. Всё, что помечено «требует подтверждения заказчика», выносим в обсуждение до
   реализации блока.
