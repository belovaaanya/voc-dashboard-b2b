# Модель данных

Дашборд статический: он не обращается к backend, а читает данные из файлов,
которые лежат рядом с сайтом.

---

## 1. Решение: xlsx — source of truth, JSON — артефакт сборки

Файлы создаются на этапе реализации — сейчас в репозитории только этот документ.

| Слой | Путь | Кто правит | В git |
| --- | --- | --- | --- |
| Source of truth | `data/*.xlsx` | аналитик, выгрузкой из источника | да, только синтетика (см. [§8](#8-репозиторий-публичный)) |
| Артефакт для браузера | `site/data/*.json` | генерируется скриптом | нет, `.gitignore` |
| Конвертер | `tools/xlsx_to_json.py` | разработчик | да |

**Почему не читать xlsx прямо в браузере.** `.xlsx` — ZIP с XML внутри; parser
для него весит больше, чем данные дашборда, и работает на каждой загрузке
страницы. Данные меняются редко и одинаковы для всех, поэтому разбор
переносится в deploy: workflow должен запускать конвертер и выкладывать готовый
JSON.

**Почему xlsx остаётся источником.** Выгрузку делает аналитик. Excel —
единственный формат, который живёт без git и без code review.

## 2. Грань данных: одна строка = одна оценка

Выгрузка — **один плоский лист**, где строка описывает одну клиентскую оценку
вместе с её комментарием и разметкой проблемы. Никаких предагрегированных
показателей в источнике нет, и это правильно: всё, что показывает дашборд,
получается группировкой этих строк под выбранный период и фильтры.

Именно поэтому выполнимо требование «клик по карточке `VOC СБ` перестраивает
весь дашборд» ([requirements 2.2](requirements.md#22-интерактивность-проваливаться-в-контекст)):
любой срез — это просто другой фильтр по тем же строкам.

## 3. Листы выгрузки

Выгрузка состоит из **двух листов оценок** — по одному на канал, `НИБ` и `АБМ` —
и **справочников разрезов**, своих для каждого канала.

Листы оценок имеют одинаковую структуру и различаются только значением
`CHANNEL_NAME`, поэтому конвертер их объединяет в один набор строк.

### 3.1. Листы оценок

| Колонка | Смысл | Тип | Примечание |
| --- | --- | --- | --- |
| `VOC_CCODE` | идентификатор оценки | string | дедупликация и трассировка до источника |
| `APPEAL_DATE` | дата оценки | date | основная временная ось дашборда |
| `ANSWER_DATE` | дата ответа | date | **не используется** |
| `CHANNEL_NAME` | канал | string | `АБМ` / `НИБ` — по каналу разделены листы. В макете второй канал подписан `АБ-WEB`; тождественны ли `НИБ` и `АБ-WEB` — [открытый вопрос](requirements.md#5-открытые-вопросы) |
| `CLIENTSEGMENT_CCODE` | сегмент | string | `ММБ` / `СБ` / `КИБ` |
| `OPERATION_NAME` | триггер | string | **несколько значений через `;`** |
| `MARK1_VALUE` | оценка | int `1…5` | единственный числовой факт, из него считается VOC |
| `CLIENT_COMMENT` | прямая речь | string | |
| `OSLK_EXPERTISE_NAME` | прямая речь | string | чем отличается от `CLIENT_COMMENT` — [открытый вопрос](requirements.md#5-открытые-вопросы) |
| `domain` | область | string | |
| `problem_type` | тип проблемы | string | |
| `problem` | проблема | string | |

### 3.2. Справочник: триггер → КП → продукт

Приводит многозначный `OPERATION_NAME` к разрезам, которые показывает
дашборд — «Продукты» и «КП» (клиентский путь).

| Колонка | Смысл |
| --- | --- |
| триггер | ключ join, совпадает с элементом `OPERATION_NAME` |
| КП | клиентский путь |
| продукт | продукт |

**Ключ join — пара (канал, триггер).** Справочники для `НИБ` и `АБМ` разные, то
есть один и тот же триггер в разных каналах может вести к разным КП и продуктам.
Join только по триггеру, без канала, даст неверный разрез.

## 4. Что из чего считается

| Показатель дашборда | Расчёт |
| --- | --- |
| VOC за период | среднее `MARK1_VALUE` по строкам среза |
| Количество оценок | число строк |
| Количество низких оценок | строки с `MARK1_VALUE ≤ 2` |
| Динамика VOC | группировка по `APPEAL_DATE` |
| Распределение оценок 1–5 | доля строк по каждому значению `MARK1_VALUE` |
| Карточки по сегментам | группировка по `CLIENTSEGMENT_CCODE` |
| Антидрайверы, разрез «Триггеры» | `OPERATION_NAME` после split по `;` |
| Антидрайверы, разрез «Продукты» | `OPERATION_NAME` → справочник (`канал`, `триггер`) → `продукт` |
| Фильтр и разрез «КП» | `OPERATION_NAME` → справочник (`канал`, `триггер`) → `КП` |
| Тепловая карта | среднее `MARK1_VALUE` по (`APPEAL_DATE` × элемент разреза) |
| Топ проблем, карточки прямой речи | `problem`, `problem_type` |
| Таблица детализации | строки как есть |

## 5. Подводные камни

По каждому принято решение — [decisions.md](decisions.md), раздел
«Агрегация» (`D-07` … `D-12`).

### 5.1. Средние нельзя усреднять

VOC за период — среднее по **оценкам**, а не среднее дневных VOC. Второе даёт
другое число, потому что в днях разное количество оценок. При грани «одна
оценка» правильное взвешивание получается само — достаточно не агрегировать
дважды.

### 5.2. `OPERATION_NAME` — многозначное поле

Одна оценка может относиться к нескольким триггерам, поэтому после split по `;`
она попадает в несколько групп. Следствия:

- сумма оценок по триггерам **больше** общего числа оценок;
- доли по триггерам не дают 100 %;
- разрезы нельзя складывать между собой.

Это не ошибка данных, а свойство разреза, и в UI его надо не скрывать: подпись
«оценок» в разрезе триггеров означает «упоминаний», а не «уникальных оценок».

**Это же распространяется на «Продукты» и «КП»**, потому что они получаются из
триггера через справочник. Причём двойной счёт там может быть и сильнее, и
слабее: несколько триггеров одной оценки могут сойтись в один продукт (тогда
оценку нужно считать один раз) или разойтись по разным (тогда она попадёт в
несколько групп). Дедупликация по `VOC_CCODE` внутри группы обязательна.

### 5.5. Триггер, которого нет в справочнике

Join по (`канал`, `триггер`) может не найти пары — справочник отстал от
выгрузки. Молча выбрасывать такие строки нельзя: VOC в разрезе продуктов
разойдётся с VOC на карточке.

Конвертер обязан **падать или явно сообщать** список несопоставленных
триггеров, а UI — показывать их отдельной группой «без сопоставления», а не
прятать.

### 5.3. Пустая разметка

Оценка без `problem` / `domain` — нормальный случай (клиент не оставил
комментарий). Такие строки участвуют в VOC и в количестве оценок, но выпадают
из разрезов по проблемам. Выбрасывать их нельзя — VOC разъедется с карточкой;
нужна явная категория «без разметки».

### 5.4. `ANSWER_DATE` не использовать

Поле в выгрузке есть, смысла для дашборда не несёт. Ни одна ось и ни один
фильтр на него не опираются.

## 6. Чего в выгрузке нет

Выгрузка покрывает динамику VOC, распределение оценок, антидрайверы и прямую
речь. Остальное дашборду нужно, но источника не имеет. Что с каждым пунктом
делаем — [decisions.md](decisions.md), разделы «Источник данных» и «Состав
блоков» (`D-03`, `D-04`, `D-13`, `D-15`, `D-17`):

| Что нужно | Чем закрывать |
| --- | --- |
| Плановый коридор VOC | нет источника. Без него не строятся бейдж «В плане» и плановая полоса на графике — нужен отдельный лист или константы |
| `Стабильность`, `Конверсия в опрос`, `Покрытие` | нет источника — отдельная выгрузка либо вне первой версии |
| События CX-календаря | нет источника — отдельный лист |
| Инсайты и аномалии | считаются на нашей стороне из тех же оценок |
| Вклад антидрайвера в VOC (`impact_voc`) | методика не зафиксирована — [открытый вопрос](requirements.md#5-открытые-вопросы) |
| Фильтры `Роли` и `ФО` | колонок нет. Либо в выгрузку добавляются поля, либо фильтры убираются из шапки |
| Платформа (`iOS` / `Android` / web) | колонки нет, а в таблице детализации макета она есть |

### Таблица детализации: половина колонок без источника

Из девяти колонок макета выгрузка закрывает пять:

| Колонка макета | Источник |
| --- | --- |
| `Дата` | `APPEAL_DATE` |
| `Сегмент` | `CLIENTSEGMENT_CCODE` |
| `Сценарий` | `OPERATION_NAME` (требует подтверждения) |
| `Комментарий` | `CLIENT_COMMENT` |
| `Категория` | `problem` / `problem_type` |
| `ФО` | **нет** |
| `Платформа` | **нет** |
| `X-pin` | **нет**, назначение неизвестно |
| `U-pin` | **нет**, назначение неизвестно |

Фильтр `КП` и разрез «Продукты» источник получили — через справочник
([§3.2](#32-справочник-триггер--кп--продукт)).

Фильтр `Сценарии`, вероятно, и есть триггер: в таблице детализации макета
колонка `Сценарий` заполнена значениями вида «Отправка платежа», «Экспорт
выписки из раздела» — это формулировки `OPERATION_NAME`. Требует подтверждения.

## 7. Объём и стратегия загрузки

Грань «одна оценка» означает, что строк примерно столько, сколько оценок:
только по одному каналу за месяц в макете фигурирует `10 459`. За год по двум
каналам это уже сотни тысяч строк, а `CLIENT_COMMENT` — самое тяжёлое поле.

Отсюда деление артефакта на два файла:

| Файл | Что внутри | Когда загружается |
| --- | --- | --- |
| `site/data/ratings.json` | факты без текстов: дата, канал, сегмент, оценка, `domain`, `problem_type`, `problem`, триггеры | при открытии страницы |
| `site/data/verbatim.json` | тексты комментариев по `VOC_CCODE` | по требованию, при открытии прямой речи и таблицы детализации |

Плюс `site/data/manifest.json`: перечень файлов, число строк, период выгрузки и
время сборки — по нему страница показывает дату актуальности данных
([requirements 7](requirements.md#7-сквозные-вопросы-реализации), п. 10).

**Точные решения по объёму принимаются на реальной выгрузке** (`D-37`). Если
`ratings.json` окажется слишком тяжёлым, следующий шаг — не «оптимизировать
JSON», а предагрегировать в источнике по (дата × канал × сегмент × элемент
разреза), пожертвовав частью произвольности фильтров. Пока реального файла нет,
выбирать между этими вариантами рано.

Формат — массив объектов, ключи совпадают с именами колонок в нижнем регистре:

```json
[
  { "voc_ccode": "A-1", "appeal_date": "2026-05-12", "channel": "АБМ",
    "segment": "ММБ", "mark": 5, "domain": "Платежи",
    "problem_type": null, "problem": null, "operations": ["Отправка платежа"] }
]
```

`operations` — уже развёрнутый в массив `OPERATION_NAME`: split по `;` делает
конвертер, а не браузер.

### 7.1. `manifest.json`

Имена файлов данных несут хэш содержимого (`D-36`), поэтому загрузчик обязан
брать их **из манифеста**, а не составлять сам. Манифест — единственный файл с
фиксированным именем.

```json
{
  "generated_at": "2026-05-23T06:30:00Z",
  "period": { "from": "2026-04-01", "to": "2026-05-22" },
  "files": { "ratings": "ratings-439b96bb.json", "verbatim": "verbatim-454a53b1.json" },
  "rows": { "ratings": 24, "verbatim": 6 },
  "labels": [
    { "dimension": "segment", "code": "ММБ", "label": "Малый и микробизнес" }
  ]
}
```

| Поле | Обязательно | Смысл |
| --- | --- | --- |
| `generated_at` | да | время сборки; из него дата актуальности в шапке (`D-35`) |
| `period` | да | период выгрузки целиком, не выбранный пользователем |
| `files.ratings` | да | имя файла оценок с хэшем |
| `files.verbatim` | нет | имя файла текстов; без него прямая речь недоступна, остальное работает |
| `rows` | нет | число строк по файлам, для диагностики |
| `labels` | нет | справочник подписей (`D-02`): `dimension`, `code`, `label` |

`labels` лежит **в манифесте**, а не отдельным файлом: справочник мал, манифест
и так не кэшируется и загружается первым, отдельный запрос ничего не добавляет.

Отсутствие `files.ratings` — расхождение с контрактом, а не пустые данные:
загрузчик обязан падать с состоянием ошибки, называя файл. Подстановка пустого
массива недопустима — она выглядит как «нет данных за период» и маскирует
сломанный pipeline.

**Чего в контракте пока нет.** Разрезы «Продукты» и `КП` требуют результата
join `(канал, триггер) → КП / продукт` ([§3.2](#32-справочник-триггер--кп--продукт)).
Join делает конвертер (`D-12` роняет сборку на несопоставленном триггере), но в
строке оценок эти поля не описаны. До решения загрузчик читает необязательные
`cps` и `products`, а фильтры этих измерений не выводятся, если полей нет — тот
же механизм, что у `D-13`.

## 8. Репозиторий публичный

Репозиторий переведён в public, потому что на бесплатном плане GitHub Pages не
обслуживает private ([README](../README.md#deploy)). Отсюда жёсткое правило:

**В `data/` попадают только синтетические данные.** Реальную выгрузку
коммитить нельзя.

Причина не в аккуратности, а в необратимости: `data/*.xlsx` версионируется, и
файл, попавший в историю git публичного репозитория, остаётся доступным после
удаления из рабочего дерева — историю придётся переписывать, а копии могут быть
уже склонированы.

В этой выгрузке чувствительны `CLIENT_COMMENT` и `OSLK_EXPERTISE_NAME` —
дословные тексты клиентов, и `VOC_CCODE`, связывающий их с источником.

Если понадобится работать на реальных данных — сначала решение по хранению
(private репозиторий на платном плане либо непубличный источник), и только
потом выгрузка.

## 9. Тестовые данные

Реальной выгрузки нет, поэтому первый `data/*.xlsx` заполняется **выдуманными**
строками в структуре из [§3](#3-листы-выгрузки). Требования:

- **внутренняя непротиворечивость важнее совпадения с макетом.** В макете часть
  цифр не сходится ([design-validation](design-validation.md)), и повторять это
  в тестовых данных нельзя — иначе первый расчёт будет выглядеть как баг
  реализации;
- среднее `MARK1_VALUE` по срезу обязано давать то число, которое показывает
  карточка;
- доли распределения оценок дают ровно 100 %;
- часть строк — с многозначным `OPERATION_NAME`, иначе `5.2` не проверить;
- часть строк — с пустыми `problem` / `domain`, иначе не проверить `5.3`;
- диапазон дат покрывает текущий период и предыдущий аналогичный, иначе не
  проверить сравнение.

Ориентиры из макета: VOC канала `4.90` при `10 459` оценках; распределение
`5 / 7 / 10 / 25 / 53 %`; сегмент `КИБ` с единицами оценок — для проверки
индикации недостаточной выборки.

Вместе с генератором нужен скрипт проверки, падающий на нарушении любого из
условий выше — иначе расхождения всплывут уже в UI.
