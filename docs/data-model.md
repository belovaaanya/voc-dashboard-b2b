# Модель данных

Дашборд статический: он не обращается к backend, а читает данные из файлов,
которые лежат рядом с сайтом.

---

## 1. Решение: xlsx — source of truth, JSON — артефакт сборки

Схема согласована, файлы создаются на этапе реализации — сейчас в репозитории
только этот документ.

| Слой | Путь | Кто правит | В git |
| --- | --- | --- | --- |
| Source of truth | `data/voc-dashboard.xlsx` | аналитик / PO, вручную в Excel | да |
| Артефакт для браузера | `site/data/*.json` | генерируется скриптом | нет, `.gitignore` |
| Конвертер | `tools/xlsx_to_json.py` | разработчик | да |

**Почему не читать xlsx прямо в браузере.** `.xlsx` — это ZIP-архив с XML
внутри; чтобы разобрать его на клиенте, нужен parser (SheetJS и аналоги),
который весит больше, чем все данные дашборда, и работает на каждой загрузке
страницы. Данные при этом меняются редко и одинаковы для всех посетителей,
поэтому разбор переносится в deploy: workflow должен запускать конвертер и
выкладывать готовый JSON.

**Почему xlsx всё-таки остаётся источником.** Таблицы правит не разработчик.
Excel — единственный формат, который редактируется без git и без code review.

Локально данные пересобираются той же командой, что и в CI:

```bash
python3 tools/xlsx_to_json.py
```

## 2. Принцип: храним факты, показатели считаем

В таблицах лежат **дневные факты**. Всё, что видно на дашборде — значения
карточек, дельты, рейтинг антидрайверов, распределение — считается на клиенте
из фактов под выбранный период и фильтры.

Иначе требование «клик по карточке `VOC СБ` перестраивает весь дашборд»
([requirements 2.2](requirements.md#22-интерактивность-проваливаться-в-контекст))
не выполнить: предагрегированные цифры нельзя пересчитать под новый срез.

Исключение — `antidrivers_impact`: вклад антидрайвера в VOC (`−0,12`) считается
по аналитической методике, а не арифметикой на клиенте, поэтому приходит
готовым. Методика ещё не зафиксирована — см.
[открытые вопросы](requirements.md#5-открытые-вопросы).

## 3. Листы

Один лист = одна сущность. Первая строка — заголовки, имена столбцов
`snake_case`. Даты в ISO `YYYY-MM-DD`. Дробные — точка, не запятая
(форматирование под запятую — задача UI).

### 3.1. `dim_filters` — справочник фильтров

Заполняет все селекторы в шапке; UI не содержит зашитых списков.

| Столбец | Тип | Описание |
| --- | --- | --- |
| `dimension` | string | `channel` \| `segment` \| `role` \| `kp` \| `fo` \| `scenario` |
| `code` | string | код для связи с фактами |
| `label` | string | подпись в интерфейсе |
| `sort` | int | порядок в списке |

### 3.2. `voc_daily` — VOC и объём выборки по дням

Основа блока «Динамика VOC» и всех карточек VOC.

| Столбец | Тип | Описание |
| --- | --- | --- |
| `date` | date | день |
| `channel` | string | `dim_filters.code` (`channel`) |
| `segment` | string | `dim_filters.code` (`segment`) |
| `voc` | float | средняя оценка за день, 1–5 |
| `ratings_count` | int | количество оценок — обязательный контекст интерпретации VOC |
| `ratings_low_count` | int | из них низких (1–2), для «количества низких оценок» |

VOC канала за период = среднее по `voc`, **взвешенное на `ratings_count`**.
Простое среднее по дням даст другую цифру и разойдётся с картой.

### 3.3. `voc_plan` — плановый коридор

Даёт бейдж «В плане» и серую полосу плана на графике.

| Столбец | Тип | Описание |
| --- | --- | --- |
| `period_start`, `period_end` | date | границы действия плана |
| `channel`, `segment` | string | срез |
| `plan_min`, `plan_max` | float | границы коридора |

### 3.4. `metrics_daily` — прочие метрики

Long-format, чтобы добавление метрики не меняло схему.

| Столбец | Тип | Описание |
| --- | --- | --- |
| `date` | date | день |
| `channel`, `segment` | string | срез |
| `metric` | string | `stability` \| `coverage` \| `survey_conversion` |
| `value` | float | значение |

Состав метрик пересматривается
([requirements 3.1](requirements.md#31-верхние-ключевые-метрики)):
`survey_conversion` — кандидат на удаление.

### 3.5. `antidrivers_daily` — значения антидрайверов по дням

Тепловая карта (второй уровень детализации) и связь просадок с датами.

| Столбец | Тип | Описание |
| --- | --- | --- |
| `date` | date | день |
| `channel`, `segment` | string | срез |
| `dimension` | string | разрез: `product` \| `trigger` \| `role` \| `kp` |
| `item` | string | элемент разреза (`Платежи`, `Выписка`, …) |
| `voc` | float | VOC по элементу за день |
| `ratings_count` | int | объём выборки — нужен, чтобы отличить реальную просадку от шума |

### 3.6. `antidrivers_impact` — рейтинг антидрайверов

Первый уровень блока: «кто главный сейчас» и «как изменился».

| Столбец | Тип | Описание |
| --- | --- | --- |
| `period_start`, `period_end` | date | период расчёта |
| `channel`, `segment` | string | срез |
| `dimension` | string | разрез |
| `item` | string | антидрайвер |
| `impact_voc` | float | вклад в VOC, отрицательный для антидрайвера |
| `rank` | int | место в текущем периоде |
| `rank_prev` | int | место в предыдущем аналогичном периоде — даёт «было №3 → стало №1» |

### 3.7. `events` — CX-календарь

Внешние события, которыми объясняется динамика.

| Столбец | Тип | Описание |
| --- | --- | --- |
| `date` | date | день события |
| `channel` | string | канал |
| `type` | string | `release` \| `incident` \| `scenario_change` |
| `title` | string | короткое название |
| `description` | string | детали |

### 3.8. `insights` — инсайты

Блок «Инсайты» (бывший «Календарь событий»).

| Столбец | Тип | Описание |
| --- | --- | --- |
| `date` | date | дата, к которой относится инсайт |
| `channel`, `segment` | string | срез, для которого инсайт посчитан |
| `kind` | string | `voc_drop` \| `voc_growth` \| `plateau` \| `mass_incident` |
| `severity` | string | `critical` \| `positive` \| `neutral` — задаёт цвет тега |
| `title` | string | тег: «Резкое падение VOC», «Плато», … |
| `cause` | string | «Основная причина: Выписка, Платежи» |
| `delta_voc` | float | изменение VOC; знак обязан совпадать с `kind` |
| `voc_after` | float | значение VOC после события |
| `impact_score` | float | вес для сортировки «по влиянию на VOC» |

Пока инсайты приходят готовыми. Требование «инсайты пересчитываются при
фильтрации» ([requirements 3.5](requirements.md#35-календарь-событий--инсайты))
покрыто тем, что строки размечены `channel`/`segment`: UI выбирает
подходящие. Генерация под произвольный срез — задача P2.

### 3.9. `rating_distribution` — распределение оценок 1–5

| Столбец | Тип | Описание |
| --- | --- | --- |
| `period_start`, `period_end` | date | период |
| `channel`, `segment` | string | срез |
| `rating` | int | 1–5 |
| `count` | int | число оценок |
| `share` | float | доля, 0–1 |

`share` хранится рядом с `count` намеренно: доля берётся из источника, а не
пересчитывается, чтобы сумма гарантированно давала 100 %.

### 3.10. `speech_tags` — облако проблем (P2)

| Столбец | Тип | Описание |
| --- | --- | --- |
| `period_start`, `period_end` | date | период |
| `channel`, `segment` | string | срез |
| `tag` | string | размеченная проблема |
| `frequency` | int | частота упоминаний |
| `sentiment` | string | `negative` \| `neutral` \| `positive` |

Источник — размеченная прямая речь, а не все слова из комментариев.

## 4. Формат JSON

Каждый лист превращается в `site/data/<sheet>.json` — массив объектов, ключи
совпадают с именами столбцов:

```json
[
  { "date": "2026-05-12", "channel": "abm", "segment": "mmb", "voc": 4.71, "ratings_count": 412, "ratings_low_count": 18 }
]
```

Плюс `site/data/manifest.json` со списком листов, количеством строк и временем
сборки — по нему страница понимает, что данные загружены целиком.

## 5. Тестовые данные

Реальной выгрузки нет, поэтому первый `data/voc-dashboard.xlsx` заполняется
**выдуманными** данными. Требования к нему:

- **внутренняя непротиворечивость важнее совпадения с макетом.** В макете часть
  цифр не сходится ([design-validation](design-validation.md)), и повторять это
  в тестовых данных нельзя — иначе первый же расчёт на клиенте будет выглядеть
  как баг реализации;
- взвешенный по `ratings_count` VOC за период обязан давать то же число, что
  показывает карточка;
- сумма `share` в `rating_distribution` — ровно 100 % на каждый срез;
- знак `delta_voc` в `insights` совпадает с `kind`;
- каждый код в фактах присутствует в `dim_filters`.

Ориентиры из макета, которые стоит воспроизвести:

| Что | Значение |
| --- | --- |
| VOC канала АБМ за месяц | `4.90` при `10 459` оценках |
| Рейтинг антидрайверов | `Выписка −0,12`, `Платежи −0,08`, `Лояльность −0,05`, `Зарплатный проект −0,03` |
| Распределение оценок | `5 / 7 / 10 / 25 / 53 %` |
| Сегмент с малой выборкой | `КИБ` — единицы оценок, чтобы проверить индикацию недостаточного объёма |

Диапазон дат должен покрывать текущий период и предыдущий аналогичный —
иначе не проверить сравнение и колонку `rank_prev`. Presets «365 дней» и
«5 лет» на тестовых данных не проверяются: для них нужна длинная выгрузка.

Вместе с генератором нужен скрипт проверки, падающий на нарушении любого из
условий выше — иначе расхождения всплывут уже в UI.
