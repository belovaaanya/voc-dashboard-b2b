# Ядро расчётов

Чистые функции, из которых собираются все числа дашборда: период, агрегации,
разрезы, вклад антидрайвера, достаточность выборки, округление на выводе.

DOM, загрузку данных и форматирование строк ядро не знает — на входе массив
оценок в форме [data-model §7](data-model.md#7-объём-и-стратегия-загрузки), на
выходе числа.

| Модуль | Отвечает за | Решения |
| --- | --- | --- |
| [`site/js/period.js`](../site/js/period.js) | preset → диапазон дат, «предыдущий аналогичный» | `D-23`, `D-24` |
| [`site/js/metrics.js`](../site/js/metrics.js) | VOC, количество оценок, низкие, распределение, группировка | `D-07`, `D-15` |
| [`site/js/breakdown.js`](../site/js/breakdown.js) | неаддитивные разрезы, «Без разметки» | `D-08`, `D-09`, `D-11`, `D-12` |
| [`site/js/impact.js`](../site/js/impact.js) | вклад антидрайвера в изменение VOC | `D-10` |
| [`site/js/plan.js`](../site/js/plan.js) | плановый коридор: какая запись описывает срез и как читается бейдж | `D-04`, `D-22`, `D-42` |
| [`site/js/sufficiency.js`](../site/js/sufficiency.js) | достаточность выборки | `D-25` |
| [`site/js/round.js`](../site/js/round.js) | округление на выводе | `D-21` |

Тесты — `test/*.test.js`, встроенный runner:

```bash
node --test
```

Зависимостей нет и не должно появиться. `test/helpers/` — не тесты, а фикстуры и
инварианты; runner всё равно берёт их в счёт как файлы без тестов, это ожидаемо.

## 1. Что здесь считается инвариантом

Ценность слайса — не в коде, а в инвариантах: они и есть проверка, что цифра
верная, а не просто посчитанная. Каждый проверен **с двух сторон** — на
настоящей реализации обязан проходить, на нарочно сломанной обязан падать
([`test/negative-controls.test.js`](../test/negative-controls.test.js)).

| Инвариант | Что ловит | Где |
| --- | --- | --- |
| VOC считается по оценкам | усреднение дневных средних (`D-07`) | `assertAveragesRatings` |
| Сумма веса разреза равна числу оценок | целое отнесение вместо `1/N` (`D-08`) | `assertWeightSumsToRatingCount` |
| VOC разреза сводится к VOC среза | потерянные группы, двойной счёт | `assertReconcilesToSliceVoc` |
| Упоминание — уникальная оценка в группе | потерянную дедупликацию по `voc_ccode` | `assertMentionsAreUniqueRatings` |
| **Сумма вкладов равна `ΔVOC`** | произвольную формулу вклада (`D-10`) | `assertContributionsSumToDelta` |
| Вклад = эффект оценки + эффект структуры | остаток, спрятанный в вкладе | `assertEffectsSumToContribution` |
| Элемент среднего уровня не создаёт вклада | потерянный отсчёт от среднего VOC | `assertNeutralElementHasNoImpact` |
| Сравнение антисимметрично | одностороннюю точку отсчёта в методике | `assertTimeSymmetric` |
| Неполный период сравнивается с началом предыдущего | скользящее окно вместо календарного (`D-24`) | `assertPartialPeriodAligns` |
| На выводе ровно столько знаков, сколько решено | лишнюю точность (`D-21`) | `assertDisplayDigits` |
| Ни одно значение не `NaN` | деление на ноль на малой выборке (`D-25`) | `assertNoNaN` |

**Сумма вкладов — признак необходимый, но не достаточный.** Она сходится при
**любой** точке отсчёта, поэтому саму методику не закрепляет: односторонний
отсчёт (VOC прошлого периода вместо середины) сходится в сумме и при этом даёт
другие вклады по элементам. Методику держат три вещи вместе — сумма,
антисимметрия сравнения и нейтральный элемент, плюс числа, посчитанные руками
в `test/negative-controls.test.js`.

«Проверен с двух сторон» означает буквально: рядом с каждым инвариантом лежит
ломаная реализация, на которой он обязан покраснеть. Инвариант без такой пары —
не guard, а украшение.

## 2. Период (`D-23`, `D-24`)

Диапазон включительный, даты — ISO в UTC.

| preset | Диапазон | Полный, когда |
| --- | --- | --- |
| `month` | календарный месяц | сегодня — последний день месяца |
| `half-year` | календарное полугодие (`H1` / `H2`) | сегодня — последний день полугодия |
| `calendar-year` | календарный год | сегодня — `31.12` |
| `days-365` | скользящие 365 дней, кончая сегодня | всегда |
| `years-5` | текущий календарный год и четыре предыдущих | сегодня — `31.12` |

`previousPeriod` возвращает период **той же формы**, что `resolvePreset`,
поэтому «май → апрель → март» — это повторный вызов, а не потеря календарной
семантики. Для `years-5` предыдущий блок — пять календарных лет перед текущим
(`2022–2026` → `2017–2021`).

`resolvePreset` обрезает диапазон по сегодняшнему дню и помечает период
`complete: false`: диапазон, кончающийся в будущем, обещал бы данные, которых
нет.

`previousPeriod` зависит от полноты:

- **полный** календарный период сравнивается с целым предыдущим календарным
  (`D-23`): май → апрель. Длины при этом не равны — 31 против 30, и это верно;
- **неполный** сравнивается с началом предыдущего календарного, выровненным по
  числу дней (`D-24`): 10 дней мая → 1–10 апреля;
- **скользящий и произвольный** диапазон — те же `N` дней непосредственно перед
  началом.

Выравнивание по числу дней не срабатывает полностью в двух случаях:

- предыдущий календарный период **короче** (29 дней марта против февраля) —
  диапазон обрезается его концом, 1–28 февраля, и длины не равны;
- на границе **високосного** года длины равны, но диапазон сдвинут: январь–май
  2024 (131 день) сравнивается с `2023-01-01…2023-05-11`, то есть предыдущее
  окно кончается на календарный день позже.

Дата, которой не существует, роняет разбор: `2026-02-30` — это не «1 марта»
(`Date` докрутил бы её молча), а ошибка входных данных. Вывернутый
`customPeriod` тоже падает, потому что период живёт в URL (`D-31`) и правится
руками.

`defaultPeriod` раскрывает период по умолчанию из `manifest.period` (`D-41`):
месяц последней оценки, а не «по сегодня» — на фиксированных датах сэмпла часы
машины дали бы пустой дашборд. Месяц раскрывается здесь, а не читается из
`period.current`: строка `YYYY-MM` не знает, полон ли месяц, а без этого не
работает выравнивание по числу дней. Расхождение `period.current` и
`period.to` — ошибка сборки, и функция на ней падает: молчаливый выбор одного
из двух полей спрятал бы сломанный конвертер.

`half-year` и `years-5` в требованиях названы без уточнения, календарные они
или скользящие. Взяты календарными — по `D-23` и потому, что `365 дней` в том
же списке названы скользящими явно. **Требует подтверждения заказчика.**

## 3. Агрегации (`D-07`)

VOC любого среза — среднее `mark` по оценкам среза. Средние не усредняются
никогда: при грани «одна оценка» правильное взвешивание получается само.

Числа возвращаются полной точности (`D-21`). Там, где значение не определено —
пустой срез, доля от нуля оценок — возвращается `null`, а не `0` и не `NaN`:
`0` это ответ, а отсутствие ответа обязано выглядеть иначе. Счётчики при этом
честный `0` — «ноль низких оценок» это факт.

Измерения группировки не зашиты: `groupBy(ratings, select)` принимает функцию
ключа, поэтому дата, канал и сегмент — один код (и `D-01` не требует правок).

`vocDelta` — изменение VOC к предыдущему периоду; пустой любой из двух срезов
даёт `null`, а не `0`: «сравнивать не с чем» и «не изменилось» — разные ответы.

`trendOf` выводит направление из знака **округлённой** дельты, а не из
отдельного поля (`V-15`). Округление здесь не лишнее: `+0,004` иначе покажет
стрелку роста рядом с подписью `+0,00`, то есть вернёт в интерфейс ровно то
противоречие, от которого защищает `D-22`.

Порядок групп — `ru`-collation, а не порядок кодов UTF-16: иначе `Ё` встаёт
перед `А`, а строчные — после всех прописных, и список триггеров из выгрузки
читается как случайный.

## 4. Неаддитивные разрезы (`D-08`, `D-09`, `D-11`)

Разрез задаётся **проекцией** `оценка → массив ключей`. Триггеры, продукты,
`КП`, `problem` и `domain` считаются одним кодом, а справочник
триггер → продукт остаётся снаружи ядра ([data-model §3.2](data-model.md#32-справочник-триггер--кп--продукт)).

Проекция вернула пусто или пустое значение — оценка попадает в группу
**«Без разметки»** (`D-11`). Ядро не теряет оценок ни при какой проекции, и
`D-12` («Без сопоставления») — это просто другое значение, которое вернёт
проекция.

Каждая группа несёт четыре разных числа, и путать их нельзя:

| Поле | Смысл | Свойство |
| --- | --- | --- |
| `weightedCount` | оценки с весом `1/N` (`D-08`) | сумма по разрезу равна числу оценок, доли дают 100 % |
| `mentions` | упоминания, целое отнесение (`D-09`) | не меньше числа оценок; в сумму не сходится |
| `voc` | VOC группы по уникальным оценкам | то, что показывает UI |
| `weightedVoc` | VOC группы с теми же весами `1/N` | сводится к VOC среза для любой проекции |

**Дедупликация по `voc_ccode` внутри группы обязательна.** Несколько триггеров
одной оценки могут сойтись в один продукт; без дедупликации оценка попадёт в
`mentions` и в `voc` группы дважды.

Обратная сторона: оценка **без** `voc_ccode` роняет расчёт. Пустой
идентификатор схлопнул бы разные оценки в одну — тихая потеря строк, самый
дорогой класс ошибок (`D-12`), поэтому это ошибка сборки, а не разрезa. На разрезе продуктов это разница между
`3.0` и `2.33` — цифра не «немного другая», а неверная.

Сводится к VOC среза именно `weightedVoc`, а не `voc`: тождество
`Σ weightedCount × weightedVoc / Σ weightedCount = VOC среза` верно для любой
проекции, в том числе многозначной. На нём стоит разложение вклада.

## 4a. Плановый коридор (`D-22`, `D-42`)

Правило живёт в одном файле целиком, потому что его применяют и карточка
канала, и сегментные карточки: разъехавшись, они дали бы разный бейдж на одном
числе.

**Какая запись описывает срез.** Коридор задан парой (канал, сегмент) и
периодом, и запись обязана покрывать выбранный период целиком: период,
задевающий два коридора, не описан ни одним. Сегмент берётся из фильтра —
`planForSlice` — или задаётся явно сегментной карточкой — `planForSegment`.
Любой фильтр, кроме сегмента, снимает коридор: канальная цель ничего не
говорит о срезе «АБМ + Выписка» (`D-42`). Записи нет — `null`, и это штатный
ответ, а не ошибка (`D-04`).

**Как читается бейдж.** Сравнивается значение, округлённое до отображаемых двух
знаков, границы включительно (`D-22`). Границы округляются тем же правилом:
подпись коридора показывает их с двумя знаками, и сравнение с неокруглённой
границей противоречило бы собственной подписи. Граница не-число — вердикта нет:
иначе сравнение с `null` молча объявило бы «выше плана».

## 5. Вклад антидрайвера (`D-10`)

**Методика требует подписи аналитики** и потому живёт в одном файле целиком:
замена — правка [`impact.js`](../site/js/impact.js), а не поиск слагаемых по
дашборду.

VOC периода раскладывается по элементам разреза как `Σ share × level`, где
`share` — доля оценок элемента, `level` — его `weightedVoc`. Тождество точное,
поэтому изменение VOC распадается на два слагаемых на элемент:

```
эффект оценки     = Δlevel × средняя доля
эффект структуры  = Δдоля  × (средний level элемента − средний VOC периодов)
вклад             = эффект оценки + эффект структуры
```

Отсчёт эффекта структуры от среднего VOC периодов нужен для смысла, а не для
сходимости: без него элемент, у которого просто вырос вес, «вносит» изменение,
которого не было. Сумма от этого не меняется — доли обоих периодов дают
единицу, и константа сокращается. Именно поэтому у методики два инварианта.

Знак читается как в макете и `V-15`: отрицательный вклад тянул VOC вниз,
рейтинг антидрайверов — сортировка по возрастанию вклада. Элемент, которого в
одном из периодов не было, меняет только структуру: его прошлый уровень
берётся равным текущему, поэтому эффект оценки у него нулевой.

Период без данных — `delta: null` и пустой список вкладов, а не ноль.

## 6. Достаточность выборки (`D-25`)

Порог выражен через точность, а не через магическое `n`: предупреждение, когда
полуширина 95 % доверительного интервала VOC превышает порог. `sd` выборочное
(делитель `n − 1`), квантиль — Стьюдента по `n − 1` степеням свободы, для
больших выборок вырождается в `1.96`. Нормальный квантиль с выборочным `sd`
занижал бы интервал именно там, где правило и нужно: при `n = 2` в 6.5 раза.

**Значение по умолчанию `0.1` балла — заглушка до подписи аналитики**, помечена
в коде. Порог передаётся параметром, поэтому подписанное значение заменяется
правкой одной строки.

Вырожденные случаи: одна оценка — интервал не определён (`null`) и выборка
недостаточна; делить на ноль нельзя, и это проверено отдельным positive control.

**Известная слабость правила.** Все оценки одинаковые → полуширина `0` →
выборка объявляется достаточной, в том числе при `n = 2`. На шкале `1…5`
совпадение пары оценок — обычная случайность, поэтому правило через CI ровно на
самых маленьких выборках говорит противоположное тому, зачем `D-25` вводился.
Закрыть это можно только минимумом оценок, а его нельзя выбрать произвольно
(requirements 3.6). Поэтому механизм есть — параметр `minimumRatings` — а
значения по умолчанию у него нет: **ждёт подписи аналитики** вместе с порогом.

## 7. Округление (`D-21`)

Считаем в полной точности, округляем только на выводе: VOC — 2 знака,
дельта — 2, вклад — 3. Отрицательный ноль нормализуется: `−0,00` на экране —
дефект, а не значение. `NaN` и `Infinity` гасятся в `null` здесь же: округление —
последняя остановка перед DOM.

Доли распределения — целые проценты, сумма **ровно** `100` (requirements 3.7).
Поэлементное округление даёт `99` или `101`, поэтому недостающие проценты
раздаются по наибольшему остатку.

Форматирование строк (`ru-RU`, запятая, неразрывный пробел) — не здесь, а в
функции формата (`D-20`). Граница проверяется тестом: в расчётных модулях нет
ни `Intl`, ни `toLocaleString`.
