# Требования — дашборд VOC для PO B2B

Источник требований — текстовая спецификация и макеты в Figma-файле
«[D] дашборд VOC для PO B2B». Ссылки и node ID собраны в [figma-sources.md](figma-sources.md).

Документ описывает **что** должен делать дашборд. Замеры вёрстки лежат в
[design-spec.md](design-spec.md), расхождения в референсном макете — в
[design-validation.md](design-validation.md).

## 1. Контекст

Дашборд показывает VOC (Voice of Customer) по каналам B2B и служит инструментом
product owner'а: не просто витрина метрик, а **система исследования причин** —
почему VOC вырос или упал.

Ключевая формулировка из спецификации:

> Дашборд постепенно превращается из набора аналитических блоков в систему
> исследования причин.

Верхнеуровневый переключатель канала: `АБМ` / `АБ-WEB`.

### Словарь

Термины взяты из макета как есть. Расшифровки не зафиксированы в источнике и
требуют подтверждения у заказчика:

| Термин | Где встречается |
| --- | --- |
| `АБМ`, `АБ-WEB` | переключатель канала в шапке |
| `ММБ`, `СБ`, `КИБ` | сегменты в карточках метрик |
| `КП`, `ФО` | фильтры в шапке |
| Антидрайверы: `Платежи`, `Выписка`, `Лояльность`, `АЗОН`, `Реестры`, `Зарплатный проект` | heatmap / рейтинг антидрайверов |
| `CX-календарь` | источник событий для инсайтов |

## 2. Сквозные принципы

### 2.1. Период — сквозной контекст, а не фильтр

Любая аналитика VOC начинается с вопроса «за какой период смотрим данные»,
поэтому период должен быть одним из главных элементов интерфейса и заметно
выделяться в шапке.

**Архитектура периода — гибридная:**

- глобальный период задаётся сверху и действует на весь дашборд;
- отдельные блоки могут менять период/масштаб локально;
- всегда должно быть очевидно, какой период применён к конкретному блоку;
- нужна механика «сбросить всё к общему периоду».

**Быстрые предустановки периода:** месяц, полгода, текущий календарный год,
365 дней, 5 лет; список открыт для дополнения.

**Сравнение с предыдущим аналогичным периодом:** месяц к месяцу, квартал к
квакталу, неделя к неделе. Сравнение включается отдельным действием
«Сравнить», а не показывается постоянно.

### 2.2. Интерактивность: проваливаться в контекст

Элементы должны не просто показывать данные, а позволять проваливаться в
контекст. Клик по любому смысловому элементу меняет контекст всего дашборда:

| Элемент | Клик | Результат |
| --- | --- | --- |
| Карточка `VOC СБ` | → | фильтр СБ; перестраиваются график, антидрайверы, инсайты, прямая речь |
| Антидрайвер «Выписка» | → | детализация по выписке |
| Дата на графике | → | события + антидрайверы + проблематики этого дня |

Кликабельность карточки должна быть понятна визуально.

## 3. Требования по блокам

### 3.1. Верхние ключевые метрики

Текущий состав: VOC канала, VOC ММБ, VOC СБ, VOC КИБ, стабильность,
конверсия в опрос, покрытие.

**Правки:**

- **Sparkline в каждом виджете метрики** — и в большом виджете VOC канала, и в
  маленьких карточках. Цель: мгновенно считывать направление и характер
  динамики, не открывая отдельный график. Композиция карточки:
  значение → sparkline → дельта (`4.90` → ~~~ → `+0,04`).
- **Карточки кликабельны** — клик по сегменту применяет соответствующий фильтр
  либо раскрывает детализацию; остальные блоки перестраиваются под выбранный
  контекст.
- **Пересмотреть состав метрик.** «Конверсия в опрос» не является значимой
  метрикой для большинства пользователей. Кандидаты на добавление:
  - количество оценок;
  - количество низких оценок;
  - распределение оценок 1 / 2 / 3 / 4 / 5;
  - возможно, отдельный показатель по низким оценкам для КИП/СБ.

### 3.2. Динамика VOC

Один из ключевых блоков для переработки.

- **Обязательно добавить количество оценок.** Сейчас график показывает VOC, но
  не показывает объём выборки. Обоснование: VOC вырос, а количество оценок
  упало в 3 раза → рост может быть статистически незначимым. Частотность
  оценок — обязательный контекст для интерпретации VOC, а не второстепенная
  метрика.
- **Наложение дополнительных показателей:** включить/выключить частотность
  оценок; выбрать дополнительную метрику; посмотреть влияние или динамику
  конкретного продукта либо другого измерения.
- **Связь с антидрайверами.** Если в конкретный день произошла просадка VOC,
  пользователь должен быстро понять, за счёт чего:
  `21.05 → VOC ↓ → платежи / выписка / лояльность ↓`.

### 3.3. Антидрайверы

Самая существенная содержательная правка. Текущий heatmap с большим
количеством цифр и зелёно-красных ячеек сложнее, чем задача блока.

**Блок должен отвечать на два вопроса:**

1. Кто главный антидрайвер в текущем периоде?
2. Как он изменился относительно предыдущего аналогичного периода?

Примеры целевой формулировки:

> **Выписка** — главный антидрайвер, −0,12 VOC к предыдущему месяцу

> **Платежи** — главный антидрайвер → было №3 → стало №1

**Целевая структура блока:**

- на первом уровне — компактный рейтинг антидрайверов:

  | # | Антидрайвер | Влияние |
  | --- | --- | --- |
  | 1 | Выписка | −0,12 |
  | 2 | Платежи | −0,08 |
  | 3 | Лояльность | −0,05 |
  | 4 | Зарплатный проект | −0,03 |

- по раскрытию — детализация влияния, динамика, дополнительные разрезы,
  тепловая карта.

То есть: **сначала «что происходит?» → по клику «почему происходит?»**

Тепловую карту можно сохранить, но не как главный способ чтения блока — она
становится вторым уровнем детализации.

### 3.4. Единая история: график → антидрайверы → события

Сейчас календарь событий воспринимается как отдельный блок, поэтому его связь
с графиком не считывается. Нужно визуально показать, что
**график + антидрайверы + события = единая история объяснения динамики**:

```
Динамика VOC
  ↓
сигналы / антидрайверы под конкретными датами
  ↓
события / релизы / сбои
```

Пример: `21.05 — VOC ↓` → 🔴 Платежи, 🔴 Выписка, 🔴 Лояльность →
CX-календарь: сбой / релиз / изменение сценария.

### 3.5. «Календарь событий» → «Инсайты»

Не переименование, а изменение концепции блока.

**Первый этап** — инсайты формируются сравнительно просто: сопоставление с
CX-календарём, рост/падение метрик, аномальные изменения, простые выводы LLM.
Примеры:

> Оценки по зарплатному проекту снизились в 3 раза относительно предыдущего периода.

> Падение VOC связано с ростом негативных оценок по выписке.

**Далее** — блок автоматически перестраивается при изменении периода,
сегмента, региона и других фильтров: выбрали «Средний бизнес» → инсайты
пересчитались для СБ; выбрали Санкт-Петербург → пересчитались для
Санкт-Петербурга.

**Сортировка инсайтов** — два режима: по влиянию на VOC и хронологически.
Вопрос вторичный по отношению к самой механике инсайтов.

### 3.6. Индикация недостаточного объёма данных

Отдельная аналитическая задача. Если за выбранный период мало оценок,
пользователь должен понимать, что вывод может быть ненадёжным
(например: «Реестры — 50 оценок за месяц» + сигнал «⚠ недостаточный объём
выборки»).

**Порог нельзя выбирать произвольно** — он определяется
статистически/методологически. Порядок работы строгий:

1. определить критерий достаточности выборки;
2. посчитать пороги;
3. только потом проектировать визуальный индикатор.

**Где показывать** — обсуждались варианты: прямо в блоке, специальный значок,
сообщение в инсайтах («Количество оценок за выбранный период недостаточно для
надёжного вывода»). Последний вариант предпочтителен: это интерпретация
данных, а не техническое предупреждение.

### 3.7. Распределение оценок

Простая диаграмма распределения:

| Оценка | Доля |
| --- | --- |
| 1 ★ | 5 % |
| 2 ★ | 7 % |
| 3 ★ | 10 % |
| 4 ★ | 25 % |
| 5 ★ | 53 % |

Варианты размещения: отдельный верхний виджет, дополнительный вид внутри
верхнего блока, фильтруемый элемент. Связана с фильтрами: выбрали СБ →
распределение перестроилось по СБ.

### 3.8. Прямая речь → облако проблем и тегов

Автоматически формируемое облако наиболее частотных проблем и слов, которое
перестраивается при смене периода, фильтрации по сегменту, выборе продукта и
других фильтрах.

Источник — **размеченная** прямая речь клиента, а не все слова из
комментариев. Потенциальный конвейер:
`прямая речь → очистка/нормализация → выделение проблем → облако`.

Статус: концепт, не обязательная правка текущей версии.
