# Гейт слайса

Проверка в конце **каждого** слайса, а не один раз перед PR. Дефект, найденный
на границе слайса, стоит одной правки; найденный через три слайса — тянет за
собой всё, что на нём построено.

Гейт состоит из двух частей, и дизайн-часть не заменяется code review: цифры
могут быть корректны, а блок при этом не соответствовать макету, и наоборот.

## 1. Код

- [ ] Независимый review — не самопроверка тем же агентом, который писал код.
- [ ] Проверки запущены и приложены выводом, а не «должно работать».
- [ ] Guard'ы проверены с двух сторон: ломаем то, что они обязаны поймать, и прогоняем корректные случаи, которые обязаны пройти.
- [ ] Любой отрицательный результат («расхождений нет», «0») подтверждён positive control на заведомо ломаном случае.

## 2. Дизайн

**«Совпадает с макетом» — здесь не критерий.** В макете есть каталог известных
расхождений, поэтому блок сверяется с *принятым решением*, а не с картинкой.

- [ ] Блок сверён с [`design/reference/desktop-wireframe.png`](design/reference/desktop-wireframe.png) — композиция, порядок элементов, визуальный язык.
- [ ] Замеры сверены с [design-spec](design-spec.md).
- [ ] Релевантные `V-xx` из [design-validation](design-validation.md) действительно применены, а не воспроизведены как в макете.
- [ ] Новое расхождение — заведено в `design-validation.md` под новым `V`-id, а не поправлено молча «по вкусу».
- [ ] Проверено на реальных данных, а не только на удобном примере: длинные подписи, отрицательные дельты, малая выборка, пустой период.

## 3. Закрытие

- [ ] Документация блока обновлена в том же PR.
- [ ] [PROGRESS.md](../PROGRESS.md) отмечен — после проверки результата, не после начала работы.
- [ ] Вопросы и спорные места вынесены заказчику, а не решены догадкой.
